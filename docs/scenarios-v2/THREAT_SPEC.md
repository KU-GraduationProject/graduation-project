# 위협 스펙 (THREAT_SPEC) — 룰 작성자 인계용

> 이 문서는 **탐지 룰 작성자**에게 그대로 넘긴다. 1차 공격·장애 8개와 대조 5개 각각에 대해
> **세 가지만** 적는다:
> 1. **위협(또는 정상 상황) 정의** — 무슨 일이 일어나는가.
> 2. **관측 가능한 증거** — 어떤 채널(앱 로그 / nginx 로그 / 메트릭 / 네트워크 이벤트)에 어떤 흔적이 남는가.
> 3. **정답** — `threat_level` / `expected_action`(현재 조치 정책 6개 중) / *이상 조치*(비실행 라벨).
>
> **의도적으로 빼는 것:** 페이로드, 주입 속도, 강도 값, 변형, 코드 경로, 룰 이름, 임계값.
> 이것들은 시나리오 쪽(또는 룰 작성자 쪽)이 각자 정한다. 이 문서는 "무엇을 탐지해야 하는가"만 규정한다.
>
> 조치 어휘(6개): `NONE / NOTIFY / THROTTLE / RESTART / PAUSE / ISOLATE`.
> *이상 조치*(`BLOCK_PATH/LOCK_ACCOUNT/RECREATE/KILL_SESSIONS/ROLLBACK`)는 현재 정책에 없는
> 참고용 라벨이다(실행되지 않음).

---

## 1차 공격·장애 (8)

### S1-a — 입력값 공격 (앱까지 통과)
1. **위협:** 공격자가 SQL 인젝션 등 공격형 입력을 보낸다. 입구(리버스 프록시)에서 차단되지 않고
   **앱까지 도달**해 처리된다(앱은 리터럴로 다뤄 정상 응답을 돌려주고 데이터는 바뀌지 않음).
   핵심은 "막히지 않고 통과했다"는 점 — 공격 표면이 앱까지 열려 있다는 신호다.
2. **증거:**
   - nginx 로그: 액세스 로그에 공격형 입력이 실린 요청 + **정상(2xx) 응답**.
   - 앱 로그: 해당 요청이 앱에서 처리된 흔적.
3. **정답:** `critical` / `NOTIFY` / *BLOCK_PATH* (대상: 입구 경로).

### S1-c — 인증 공격 (로그인 대입)
1. **위협:** 한 계정(또는 소수 계정)에 **반복적으로 틀린 비밀번호**로 로그인을 시도한다(대입/추측).
   계정 잠금 로직이 없어 시도는 계속 실패 로그만 남긴다.
2. **증거:**
   - 앱 로그: 짧은 시간에 몰린 **인증 실패 로그**. (실패 사유·계정 식별자가 로그에 남을 수 있음.)
3. **정답:** `medium` / `NOTIFY` / *LOCK_ACCOUNT* (대상: 공격받는 계정).

### S2-a — 자원 탈취 (채굴형 CPU)
1. **위협:** 침해된 프로세스가 **CPU 를 지속적으로 점유**한다(암호화폐 채굴 등). 서비스는 죽지 않고
   살아 있지만 자원을 빼앗긴다.
2. **증거:**
   - 메트릭: 대상 컨테이너의 **CPU 사용률이 비정상적으로 높게 지속**.
   - 앱 로그: 서비스는 계속 정상 응답(가용성은 유지).
3. **정답:** `high` / `THROTTLE` / *RECREATE* (대상: 침해된 서비스 컨테이너).

### S2-c — 데이터 반출 (비인가 목적지 전송)
1. **위협:** 내부 서비스가 **비인가 목적지로 대량 데이터를 전송**한다. 전송량·방식이 아니라
   **목적지가 허용 목록 밖**이라는 점이 공격의 핵심이다(동일 전송을 인가 목적지로 하면 정상 = C-a).
2. **증거:**
   - 네트워크 이벤트: 내부 서비스 → **비인가 외부/내부 목적지**로의 전송(누적 전송량 포함).
3. **정답:** `critical` / `ISOLATE` / *ISOLATE* (대상: 송신 서비스).

### F1-b — 메모리 압박·누수 (서서히)
1. **위협:** 서비스가 회수되지 않는 메모리를 **서서히 쌓아** 압박 상태가 된다(누수). 급격한 스파이크가
   아니라 시간에 걸쳐 누적되며, 재기동 전까지 **자가 치유되지 않는다**.
2. **증거:**
   - 메트릭: 대상 컨테이너의 **메모리 사용량(working set)이 상승해 높은 수준으로 유지**.
3. **정답:** `medium` / `RESTART` / *RESTART* (대상: 해당 컨테이너).

### F2-a — MinIO 중단
1. **위협:** 오브젝트 스토리지(MinIO)가 **중단**돼 사용 불가가 된다(프로세스/컨테이너 다운).
   데이터 삭제가 아니라 **가용성 상실**이다.
2. **증거:**
   - 메트릭: 스토리지의 **가용성 신호가 끊김**(수집 대상 down).
   - 앱 로그: 스토리지에 접근하는 서비스의 **연결/요청 오류 로그**.
3. **정답:** `medium` / `RESTART` / *RESTART* (대상: 스토리지 서비스).

### F2-c — DB 연결 한도 고갈
1. **위협:** 외부 세션이 PostgreSQL **연결 한도(max_connections)**를 소진한다. 앱 커넥션 풀이
   아니라 **DB 서버의 연결 슬롯**이 바닥나 새 연결이 거부된다. 미리 연결을 열어 둔 서비스는
   한동안 정상일 수 있다.
2. **증거:**
   - DB 로그: **새 연결 거부 메시지**(too many clients).
   - 메트릭: DB **연결 수가 한도에 붙어** 유지.
   - 메트릭: 새 연결을 여는 클라이언트(postgres-exporter 등)의 **수집 실패**.
   - 앱: backend 는 미리 열어 둔 연결로 **한동안 정상 응답**(이후 지연·실패로 악화).
3. **정답:** `high` / `NOTIFY` / *KILL_SESSIONS* (대상: 점유 중인 DB 세션).

### F3-a — 잘못된 이미지 배포
1. **위협:** 서비스가 **깨진 이미지/태그로 배포**돼 기동에 실패한다(crashloop 또는 헬스 체크 실패).
2. **증거:**
   - 메트릭: 대상 컨테이너의 **반복 재시작**.
   - 앱 로그: **기동 실패/헬스 실패 로그**.
3. **정답:** `high` / `NOTIFY` / *ROLLBACK* (대상: 배포된 서비스).

## 대조 (5) — "발화 없음(또는 알림만)"이 정답

### C-a — 인가 목적지 대량 전송
1. **정상 상황:** 내부 서비스가 **허용 목록 안의 목적지로** 대량 데이터를 전송한다. 전송량·방식은
   S2-c 와 같지만 목적지가 인가돼 있어 정상 운영이다.
2. **증거:** 네트워크 이벤트 — 인가 목적지로의 전송.
3. **정답:** `low` / `NONE` / *NONE* (경보 없음이 정답).

### C-g — JVM 평상시 메모리
1. **정상 상황:** 서비스가 **평상시 부하에서 정상 범위의 메모리**를 쓴다(누수 없음).
2. **증거:** 메트릭 — 메모리 사용량이 정상 범위에서 오르내림.
3. **정답:** `low` / `NONE` / *NONE* (경보 없음이 정답).

### C-n — AIOps 자체 부하 (모델 다운로드)
1. **정상 상황:** AIOps 구성요소가 **모델 다운로드 등 자체 작업**으로 네트워크/자원을 쓴다.
   보호 대상 서비스의 공격이 아니라 운영 트래픽이다(출발지가 보호 대상 서비스가 아님).
2. **증거:** 네트워크 이벤트 — 출발지가 보호 대상 서비스가 아닌 트래픽.
3. **정답:** `low` / `NONE` / *NONE* (경보 없음이 정답).

### C-c — 이미 차단된 공격 (4xx 다발)
1. **정상(방어 성공) 상황:** 공격 시도가 **입구에서 이미 차단**돼 4xx 로 거절된다. 방어가 동작한
   경우라 조치는 알림 수준이면 충분하다(앱까지 통과한 S1-a 와 대비).
2. **증거:** nginx 로그 — **4xx 응답이 몰린** 액세스 로그.
3. **정답:** `low` / `NOTIFY` / *NOTIFY*.

### C-e — 비밀번호 오입력
1. **정상 상황:** 정상 사용자가 비밀번호를 **가끔 틀린다**(소수의 산발적 인증 실패, 곧 성공).
   S1-c 대입 공격과 구분돼야 하는 음성 대조다.
2. **증거:** 앱 로그 — **소수의 인증 실패 로그**(산발적).
3. **정답:** `low` / `NONE` / *NONE* (경보 없음이 정답).
